## Goal

Commands in the existing `talent_data` package (CLI `talent-data ota …`) that turn a committed
build in `data/` into a published OTA release on static storage, with every gate of the publisher
design, staging and production channels, rollback and live verification. Everything must work
against a local directory standing in for the bucket, so all tests run offline without cloud
accounts.

## Scope

1. `src/talent_data/ota/release.py` — `build_release(repo_root, commit, game, build, revision,
   created_at, validation_note) -> (manifest_bytes, {sha256: bytes})`. Reads files **at the
   commit** (`git show <commit>:<path>` or `git archive`), not from the working tree.
   Deterministic.
2. `src/talent_data/ota/gates.py` — gates G1–G8 as functions with typed results
   (`GateResult(gate, status: PASS | FLAG | STOP, detail)`). G3 calls `verify_release_manifest`
   and `verify_release_files`; G4 compares with every published release of the build and,
   read-only, with the bundled copy under `mobile/composeApp/src/commonMain/composeResources/files/`;
   G5 compares `warningsByCode`; G6 compares the allocation inventory (reuse
   `scripts/allocation_inventory.py`, moving its logic into the package if needed).
3. `src/talent_data/ota/catalog.py` — build the next catalog from the live one: append a release,
   set the active one, roll back, re-sign (new `sequence`, `issuedAt`, `expiresAt`), enforcing
   contract §6.1 #12 and the append-only rule of §4 (refuse to drop or alter a listed release).
4. `src/talent_data/ota/signing.py` — envelopes from an **external** signature: `promote` writes
   the payload and prints the SHA-256 of its PAE; `attach-signature` takes a DER signature file,
   verifies it with the committed public key and only then writes `catalog.json`. A convenience
   `sign --key <pem>` is allowed **for staging and tests only** and must refuse production key
   ids.
5. `src/talent_data/ota/store.py` — a `BlobStore` protocol with `LocalDirectoryStore` (tests,
   dry runs) and one S3-compatible implementation over the existing `httpx` dependency (if
   request signing makes it too large, ship only the protocol + local store and document the
   gap). Order: blobs first, each verified by reading it back; catalog last; check the live
   `sequence` before writing the catalog (`If-Match` where available). Set the `Cache-Control`
   values of contract §1.
6. CLI `talent_data/cli/ota.py`: `ota build-release`, `ota validate`, `ota report`, `ota stage`,
   `ota promote`, `ota attach-signature`, `ota rollback`, `ota resign`, `ota verify-live`,
   `ota gc`. Every mutating command defaults to a dry run; writing needs `--execute`; `gc` also
   needs `--confirm` and lists what it would delete.
7. Approval records per [OD-12](open-decisions.md): `promote` refuses when a gate flagged and no
   record for the release id exists.
8. `docs/ota/publisher-runbook.md` — operator procedures: first publication, routine refresh,
   rollback, re-sign, key loss, key compromise, hosting change.
9. `cryptography` (already in the `ota` extra) stays the only new dependency; `talent_data` and
   its other commands must still import without it (lazy import in the OTA CLI).

## Out of scope (do not do)

* Any Kotlin/mobile change, the OTA client, UI.
* Creating cloud accounts, buckets, DNS records or keys; uploading anything to a real host.
* Generating or committing production keys; reading production private keys from the
  repository or a CI environment.
* Automatic publication from the freshness watcher, cron or CI.
* Changing existing `docs/schema/*`, the OTA contract, normalized data, the allocation engine
  or `docs/talent-allocation-semantics.md`.
* Deleting any `data/` build or bundled dataset.

  `python scripts/generate_ota_fixtures.py --check` green.
