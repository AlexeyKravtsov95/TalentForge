# M8.OTA.HOTFIX.2 — reliable delivery after authorization

## Root causes

1. `ota-release-prepare.yml` passed `--auto-data-only` to `ota_premerge.py`.
   That flag belongs to `ota_release_automation.py propose-request`. Premerge has a
   separate conditional owner-merge protocol; its binding/readiness checks must run.
2. CI completion starts preparation and publication concurrently. The publisher can
   finish `WAIT / APPROVAL_PENDING` before preparation freezes its authorization.
   The publisher subscribed only to CI completion, so authorization emitted no wakeup.
   Adding another `workflow_run` link would also inherit GitHub's three-level limit.
3. Preparation deduplicated by an artifact key containing main SHA, not by whether
   the candidate's dataset was already merged. A later main SHA re-downloaded merged,
   unpublished data. Release-package selection also ignored an existing data-only tag,
   allowing a later main SHA to start a redundant staging/package pair. Both selection
   boundaries now retain the reviewed data and frozen authorization. Source availability
   was incorrectly coupled to delivery progress.
4. Probe intentionally returned exit 0 for routing decisions, while `WAIT` skipped
   the result and notification jobs. A green scheduler could look like completed delivery.
5. Timing evidence looked only for approval files. Tag-only standing authorization
   therefore produced a different fingerprint from the probe, preventing failed runs
   from counting toward the same-input cooldown/retry budget. The recorder now binds
   the exact standing authorization bytes; it leaves the unproven approval clock null.

## Delivery protocol

The standing-policy path first persists the unchanged immutable
`ota-data-only/<releaseId>` annotated request tag, then calls `POST /dispatches` with
only `event_type=ota-delivery-authorized`. Existing repository-scoped App Contents
write permission is sufficient. No new credentials or App permissions are introduced.
The event does not carry an executable ref, request, artifact, approval or CI pin.

`repository_dispatch` is a wakeup only. The production workflow checks the default
branch, invocation/API identity and event type, fetches exact request tags, and
independently proves current-main CI, exact request/source CI, policy, package/staging
provenance, live base and G1–G8 before reading production secrets. Existing protected
writer serialization, durable journal, signing, read-back and independent public
verification are unchanged. The legacy owner-merge path still wakes after main CI.

An interrupted/lost dispatch response leaves the tag intact. A retry reuses that tag
and repeats only the wakeup. The five-minute scheduled probe discovers authorized
requests even when the event is lost; GitHub can delay scheduled starts. Duplicate
events cannot change a verified receipt or allocate another sequence. Recovery of
`WRITE_STARTED` / `AMBIGUOUS` takes priority, and `PUBLISHED_NOT_VERIFIED` selects
verification rather than a fresh publication.

GitHub documents the dispatch recursion exceptions and workflow chain bound:
[GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token),
[workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows).

## Separate lifecycles and diagnostics

| Observed fact | Meaning / next step |
| --- | --- |
| New publishable index build | Not prepared; source preparation can run |
| Retained PREPARED artifact | Prepared; propose/reuse the candidate PR |
| Candidate dataset committed on main | `MERGED`; do not repeat source preparation |
| Valid merged approval or immutable standing-policy tag | Authorized; publisher independently assesses it |
| PENDING/PREPARED journal receipt | Awaiting publication / publication planning |
| WRITE_STARTED or PUBLISHED_NOT_VERIFIED | Recover or verify exact retained work |
| VERIFIED / PUBLIC_VERIFIED receipt | Delivery confirmed; no second publish |

Preparation's `NO_ACTION / MERGED` does not claim publication. Only explicit `--force`
can ask source preparation to repeat. Historical replay reconstructs the pre-patch
committed-build inventory as well as the historical index, bundle and catalog.

The production `delivery-status` job summarizes eligible automatic runs separately from
successful probe execution. The existing minimal `delivery-result` audit remains
independent of the writer, so a partial preflight refusal cannot wait behind a queued
writer. Consumer reruns download each retained producer's exact artifact ID:

| State | Evidence |
| --- | --- |
| NO_WORK | No selected pending operation |
| WAIT | External condition, with the probe's actual reason; a warning, not a publication claim |
| BLOCKED | Refusal, missing/interrupted evidence, partial failure or ambiguous outcome; result job fails |
| PUBLISHING | READY work or publication awaiting independent public proof |
| PUBLIC_VERIFIED | Nonempty operation set verified by the guarded publication command |

WAIT notifications use the existing notification environment and durable deduplication;
even a first WAIT observation alerts, never announces production success. An automatic
run with an active preflight/writer older than two hours becomes
`BLOCKED / DELIVERY_STALLED`; it alerts without cancelling the writer or resetting its
retry budget. A later turn can recover exact durable work once the old run completes.
The first stall observation also alerts when the notification marker is absent.
Disabled discovery reports WAIT / DISABLED, since it has not established absence of work.

## P1 follow-up: historical approval must not mask a retained base refusal

Scheduled [probe 44973647788](https://github.com/AlexeyKravtsov95/TalentForge/actions/runs/44973647788)
on main `7dff031e3028` reported `WAIT / APPROVAL_PENDING` after 71037 was verified.
The historical 70755 request still points to base 70707 and its approval has OWNER
placeholders. Probe examined that incomplete approval before its retained
`BLOCKED / LIVE_CHANGED` receipt, so it never reached the base check.

For retained `LIVE_CHANGED` / `ALREADY_LISTED` refusals, probe now checks the signed
public catalog hint first. A mismatched or unavailable base reports the existing
`WAIT / BASE_NOT_CURRENT`, without package/history work or journal writes. It does
not claim NO_WORK, a terminal STALE receipt or PUBLIC_VERIFIED from a public hint:
only the protected publisher owns authoritative live/terminal decisions. When the
base is current again, the full approval, CI, package and retry checks still apply;
missing/incomplete approval remains `WAIT / APPROVAL_PENDING`. Retained uncertain
writes and pending public verification keep their recovery priority.

The regression matrix covers both refusal reasons, missing/placeholder approval and
mismatched/current/unavailable catalog hints. Before the fix, eight stale/unavailable
cases incorrectly returned APPROVAL_PENDING; four current-base cases already preserved
the required authorization wait. All twelve cases passed after the reorder; the combined
probe, reconciliation and delivery-status suite passed all 77 tests. Ruff, formatting,
mypy and diff whitespace checks also passed. Full local `pytest -n 4 -o
tmp_path_retention_policy=failed`: **3576 passed in 641.48 s**.

A local read-only probe using the fixed code against main `7dff031e3028` and the real
Git journal returned `WAIT / BASE_NOT_CURRENT`: signed public catalog active 71037-r1,
sequence 9; historical 70755-r1 receipt `BLOCKED / LIVE_CHANGED`; 71037-r1 receipt
`VERIFIED / PUBLIC_VERIFIED`. The journal's exact SHA-256 was unchanged before/after.
The harness refused API mutations, journal saves and archive downloads; it did not run
a production workflow or publisher. [Read-only evidence](evidence/m8-ota-hotfix-2/stale-base-readonly-probe.json)
binds the result to the probe source SHA-256. This is a local assessment, not a claim
that main already contains the fix.
