# M5.OTA.3 — OTA client in the KMP app (brief for Opus)

Branch: `feature/m5-ota-3-client` from `main` after M5.OTA.1 is merged (M5.OTA.2 is not required).
PR title: `M5.OTA.3: Remote dataset client (verify, install, activate, pin, retain)`.
The client is built and fully tested without the publisher and without hosting: every test uses
the committed fixtures and an in-memory blob store.

## Goal

The app keeps opening instantly on local data, checks for a new release in the background,
installs it only after full verification, activates it atomically for **new** sessions, keeps
open editors and saved builds on their own datasets, downloads historical releases on demand, and
never loses or rewrites a saved build.

## Scope

### `mobile/shared` (pure KMP, no new dependency)

1. `data/ota/OtaContract.kt` — strict kotlinx.serialization models for `ota-envelope.v1`,
   `ota-catalog.v1`, `ota-release.v1` under the existing strict `Json` policy, plus: rejection of
   duplicate object keys (check whether the configured `Json` already rejects them; if not, detect
   them in a `JsonElement` pre-pass), canonical base64, UTC timestamps.
2. `data/ota/OtaFailure.kt` — a sealed type with one member per contract error code (names equal
   to `OtaErrorCode`), plus client-only `Network`, `Http(status)`, `InsufficientStorage`, `Io`,
   `Cancelled`.
3. `CatalogVerifier`, `ActivationPolicy`, `ReleaseVerifier`, `ReleaseValidator`, `RetentionPolicy`,
   `OtaState` (+ strict codec), `DatasetSnapshot`, and the ports `SignatureVerifier`, `BlobFetcher`,
   `OtaFileStore`, `OtaClock` — client design §2. Move `sha256Hex` to a neutral file and add a
   streaming variant.
4. **Kotlin conformance replay** (jvmTest; also an iOS simulator test if the module gets one): read
   `docs/ota/fixtures/v1/cases.json` — synced into test resources by a script with a `--check`
   drift mode, like the dataset sync — and assert the same verdict and code for all 56 cases, with
   a JVM `SignatureVerifier`.

### `mobile/composeApp`

5. Platform adapters (androidMain, iosMain, desktopMain):
   * `PlatformSignatureVerifier` — `java.security.Signature("SHA256withECDSA")` with
     `X509EncodedKeySpec`; iOS `SecKeyCreateWithData` (the 65-byte X9.63 point = last 65 bytes of
     the SPKI) + `SecKeyVerifySignature(kSecKeyAlgorithmECDSASignatureMessageX962SHA256)`;
   * `PlatformBlobFetcher` — HttpURLConnection / ephemeral NSURLSession / java.net.http; byte
     limits enforced while reading; no redirect to another host;
   * `PlatformOtaFileStore` — Android `noBackupFilesDir/ota`; iOS Application Support, excluded
     from backup; atomic rename and replace per client design §3.
6. `OtaConfig` per build type (client design §8) with `enabled`. Base URLs and keyrings are
   Gradle-generated constants that **keep OTA disabled** until the owner supplies hosting and
   public keys ([OD-1](open-decisions.md), [OD-2](open-decisions.md)).
7. `RemoteDatasetCatalog`, `DatasetDownloadManager`, `DatasetCache`, `DatasetActivationManager`,
   `OtaUpdateCoordinator`, `ReleaseAssetSource`, `RoutingDatasetAssetSource` — client design §2, §4.
8. Wiring in `App.kt`: recovery before the first screen, `StateFlow<DatasetSnapshot>`, background
   check after the first frame and on return to the foreground (6 h), one attempt at a time.
9. `BuildLoaders.kt`: `loadEditorSession`, `createClassDraft`, New Build and build cards take a
   `DatasetSnapshot`; new drafts use `snapshot.product`; a missing dataset resolves per client
   design §5.2 to the typed `DatasetUnavailable(reason)` with Retry. `prepareBuildImport` uses the
   same resolution.
10. `BUNDLED_CLIENT_BUILDS` constant, drift-checked by `scripts/mobile_bundles.py --check`.
11. Android `INTERNET` permission. Minimal UI only: the typed unavailable state with reason and
    Retry, download progress for an on-demand historical build, and (per
    [OD-5](open-decisions.md)) one "talent data updated to 1.60.x" line and a "check now" action on
    an existing surface. Follow the frozen B3 contract and the UX/UI spec; no other UI change.
12. `docs/mobile-architecture.md`: a "Remote datasets (M5.OTA.3)" section; update "Bundled
    datasets" for the product vs. rollback-floor distinction.

## Out of scope (do not do)

* Publisher code, hosting, keys, uploads (M5.OTA.2 / owner).
* Changing the OTA contract, existing schemas, normalized data, the allocation engine,
  `docs/talent-allocation-semantics.md` or the saved-build format.
* Migrating, re-binding or rewriting saved builds; opening a build on any build but its own.
* Removing bundled datasets; enabling OTA in a store build (needs test-plan §6).
* Background schedulers (WorkManager, BGTaskScheduler), analytics, crash reporting, DI
  frameworks, Ktor or okio (unless [OD-11](open-decisions.md) decides otherwise), release
  signing changes.
