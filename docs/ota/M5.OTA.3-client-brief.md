# M5.OTA.3 — OTA client in the KMP app (brief for Opus)

Branch: `feature/m5-ota-3-client` from `main` after M5.OTA.1 is merged (M5.OTA.2 is not required).

The client is built and fully tested without the publisher and without hosting: every test uses
the committed fixtures and an in-memory blob store.

## Goal

The app keeps opening instantly on local data, checks for a new release in the background,
installs it only after full verification — resuming interrupted downloads without fetching
verified files again — activates it atomically for **new** sessions, keeps open editors and saved
builds on their own datasets, downloads historical releases on demand, and never loses or rewrites
a saved build.

## Scope

### `mobile/shared` (pure KMP, no new dependency)

1. `data/ota/JsonDuplicateNames.kt` — the **duplicate-name scanner** of contract §2.1: a lexer over
   the raw UTF-8 bytes that tracks string tokens, object/array nesting and the member-name position
   in each object, unescapes names (including `\uXXXX` and surrogate pairs) and keeps one name set
   per open object, with a bounded nesting depth. It runs **before** any decoding of every OTA JSON
   document and of every JSON file of a release. Do not rely on `JsonElement`/`JsonObject` (a map:
   duplicates are already lost) or on the typed decoder's behaviour. Stage codes: envelope →
   `ENVELOPE_INVALID`, catalog payload → `PAYLOAD_INVALID`, release manifest → `MANIFEST_INVALID`,
   release content file → `CONTENT_INVALID`. A third-party library is acceptable only if it exposes
   raw member names in source order on Android, iOS and the JVM; record that decision in the PR.
2. `data/ota/OtaContract.kt` — strict kotlinx.serialization models for `ota-envelope.v1`,
   `ota-catalog.v1`, `ota-release.v1` under the existing strict `Json` policy, plus canonical base64
   and UTC timestamps.
3. `data/ota/OtaFailure.kt` — a sealed type with one member per contract error code (names equal to
   `OtaErrorCode`, including `CATALOG_TOO_LARGE`) plus client-only `Network`, `Http(status)`,
   `InsufficientStorage`, `Io`, `Cancelled`, and the classification of client design §4.7
   (transient vs. release rejected for what it is).
4. `CatalogVerifier` (size first: more than 1 MiB → `CATALOG_TOO_LARGE`), `ActivationPolicy`,
   `ReleaseVerifier`, `ReleaseValidator`, `RetentionPolicy`, `OtaState` (+ strict codec, including
   rejected releases), `StagingPolicy` (the decisions of client design §4.7 as a pure function of
   the staging listing, `attempt.json`, the verified catalog entry and free space),
   `DatasetSnapshot`, and the ports `SignatureVerifier`, `BlobFetcher` (with a hard `maxBytes`),
   `OtaFileStore`, `OtaClock` — client design §2. Move `sha256Hex` to a neutral file and add a
   streaming variant.
5. **Kotlin conformance replay** (jvmTest; also an iOS simulator test where the module has one):
   read `docs/ota/fixtures/v1/cases.json` — synced into test resources by a script with a `--check`
   drift mode, like the dataset sync — and assert the same verdict and code for all 64 cases with a
   JVM `SignatureVerifier`. Mandatory among them: every duplicate-name case
   (`catalog-envelope-duplicate-key`, `catalog-envelope-nested-duplicate-key`,
   `catalog-duplicate-json-key`, `catalog-duplicate-key-same-value`, `catalog-duplicate-nested-key`,
   `catalog-duplicate-escaped-key`, `release-duplicate-nested-key`, `release-content-duplicate-key`)
   and `catalog-over-size-limit`; plus a boundary test that a catalog of exactly 1 MiB is verified
   normally.

### `mobile/composeApp`

6. Platform adapters (androidMain, iosMain, desktopMain):
   * `PlatformSignatureVerifier` — `java.security.Signature("SHA256withECDSA")` with
     `X509EncodedKeySpec`; iOS `SecKeyCreateWithData` (the 65-byte X9.63 point = last 65 bytes of
     the SPKI) + `SecKeyVerifySignature(kSecKeyAlgorithmECDSASignatureMessageX962SHA256)`;
   * `PlatformBlobFetcher` — HttpURLConnection / ephemeral NSURLSession / java.net.http; the byte
     limit is enforced **while reading** (stop at the limit + 1 byte; never buffer the rest); no
     redirect to another host;
   * `PlatformOtaFileStore` — Android `noBackupFilesDir/ota`; iOS Application Support, excluded from
     backup; atomic rename and replace per client design §3; `.part` writes and renames.
7. `OtaConfig` per **platform** and build type (client design §8) with `enabled`. Base URLs and
   keyrings are Gradle-generated constants that **keep OTA disabled** until the owner supplies
   hosting and public keys ([OD-1](open-decisions.md), [OD-2](open-decisions.md)); Android and iOS
   are enabled independently ([OD-17](open-decisions.md)).
8. `RemoteDatasetCatalog`, `DatasetDownloadManager` (staging, resume, reuse with re-hash),
   `DatasetCache`, `DatasetActivationManager` (with `recover()` exactly as client design §4.1 and
   §4.7), `OtaUpdateCoordinator`, `ReleaseAssetSource`, `RoutingDatasetAssetSource` — client design
   §2, §4.
9. Wiring in `App.kt`: recovery before the first screen, `StateFlow<DatasetSnapshot>`, background
   check after the first frame and on return to the foreground (6 h), one attempt at a time.
10. `BuildLoaders.kt`: `loadEditorSession`, `createClassDraft`, New Build and build cards take a
    `DatasetSnapshot`; new drafts use `snapshot.product`; a missing dataset resolves per client
    design §5.2 to the typed `DatasetUnavailable(reason)` with Retry. `prepareBuildImport` uses the
    same resolution.
11. `BUNDLED_CLIENT_BUILDS` constant, drift-checked by `scripts/mobile_bundles.py --check`.
12. Android `INTERNET` permission. Minimal UI only: the typed unavailable state with reason and
    Retry, download progress for an on-demand historical build, and (per
    [OD-5](open-decisions.md)) one "talent data updated to 1.60.x" line and a "check now" action on
    an existing surface. Follow the frozen B3 contract and the UX/UI spec; no other UI change.
13. The performance measurements of test-plan §7 (a JVM benchmark with injected latency, bandwidth
    and loss, plus Android emulator throttling); results in the PR and in `docs/ota/`, stating
    whether any §7.3 trigger fired. Do not implement batching or archives.
14. `docs/mobile-architecture.md`: a "Remote datasets (M5.OTA.3)" section; update "Bundled
    datasets" for the product vs. rollback-floor distinction.

## Out of scope (do not do)

* Publisher code, hosting, keys, uploads (M5.OTA.2 / owner).
* Changing the OTA contract, existing schemas, normalized data, the allocation engine,
  `docs/talent-allocation-semantics.md` or the saved-build format.
* Migrating, re-binding or rewriting saved builds; opening a build on any build but its own.
* Removing bundled datasets; enabling OTA in a store build (needs the gates of test-plan §6).
* Background schedulers (WorkManager, BGTaskScheduler), analytics, crash reporting, DI
  frameworks, Ktor or okio (unless [OD-11](open-decisions.md) decides otherwise), archive or batch
  delivery, release signing changes.

  verdicts, including every duplicate-name case and the size limit.
* L2 tests for S1–S14 and test-plan §3 are green. S5 and S10 prove on the request log that a

  release gate (test-plan §6C).

* With OTA disabled, every existing test is unchanged and green, and the app behaves as before.
