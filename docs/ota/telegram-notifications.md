# Личные Telegram-уведомления владельцу (M5.NOTIFY)

Персональные уведомления владельцу TalentForge о новых игровых данных и ходе OTA — через
Telegram Bot API, из существующих workflows. Отдельный постоянно работающий сервер не
нужен: всё исполняется в GitHub Actions, публикация production остаётся ручной
процедурой владельца ([publisher-runbook.md](publisher-runbook.md)) — этот документ её
не меняет.

## Четыре события

| # | Событие | Откуда | Сообщение (русское) | Дедупликация |
| --- | --- | --- | --- | --- |
| 1 | Обнаружен новый игровой билд | `Dataset freshness` (ежедневно, job `notify`) | версия, источник (`is_bgdl=false`), `PRODUCT_BUNDLE`, ссылка на tracking issue | один раз на версию билда (`freshness.json`) |
| 2 | Кандидат OTA подготовлен | `OTA data preparation` (job `notify`) | releaseId, база, итог проверок (шаги, гейты, требуемые шаги), ссылка на PR или артефакт | один раз на releaseId (`candidate.json`) |
| 3 | Production OTA обновился | `OTA production watch` (ежечасно) | активный releaseId, sequence, результат проверки публичного endpoint | один раз на активный releaseId (`production.json`) |
| 4 | Подготовка или проверка сломалась | все три выше | этап, короткая причина, ссылка на запуск | один раз на эпизод сбоя этапа |

Два обязательных дисклеймера всегда в тексте: наличие билда в индексе wago.tools — не
подтверждение версии игровых серверов (событие 1), и `PREPARED` — не разрешение на
production-публикацию (событие 2). Ожидаемый `OUTDATED` проверки свежести событием 4 не
считается: это и есть событие 1.

## Где живут джобы уведомлений

* `dataset-freshness.yml`, job `notify` — после обновления tracking issue (его URL идёт в
  сообщение). Читает артефакт `freshness-report` этого же запуска.
* `ota-prepare.yml`, job `notify` — после `prepare`/`propose`. Читает артефакт этого же
  запуска (`report.json`, `detection.json`), берёт ссылку на PR из outputs `propose`.
* `ota-production-watch.yml` — новый ежечасный workflow (cron `23 * * * *`). Read-only
  наблюдение публичного каталога `https://ota.mythweld.com/v1/channels/production/catalog.json`:
  анонимный GET, проверка подписи референс-верификатором против
  `docs/ota/keys/production-keyring.json` (`tf-prod-*`), затем загрузка и перепроверка
  манифеста активного релиза против пина каталога. При первом baseline и смене active
  watcher дополнительно проверяет **все** listed manifests и referenced files существующим
  reference verifier (хеши, размеры, identity, completeness, same-build identity), затем
  повторно читает каталог и требует неизменный signed payload. Чтение ограничено размерами
  контракта и manifest pins; redirect/credentials не используются. Повреждённый/отсутствующий
  blob или сменившийся каталог запрещают success и изменение `notifiedRelease`. Такой первый
  запуск остаётся молчаливым, но успешный baseline не фиксируется: после восстановления
  следующий запуск сообщает один раз. При неизменном active полная загрузка blobs не нужна;
  простая переподпись не считается обновлением. Уведомление — только когда после всей
  проверки изменился **активный releaseId**; переподпись каталога или новый sequence с тем
  же активным релизом — не выпуск. Каталог `UNKNOWN` (не читается/не проверяется) или
  исчезнувший после публикации — событие 4.
* `telegram-smoke-test.yml` — ручной smoke-test (ниже).

## Долговечная дедупликация

Состояние — три маленьких JSON-документа на ветке **`telegram-notify-state`**
(`freshness.json`, `candidate.json`, `production.json`), коммитит их сам скрипт
(`talent_data.notify.gitstate`): push проигравший гонку перебазируется и повторяется
(до 3 раз). Это не Actions cache и не артефакт — ничего не испаряется и не истекает.

* **Первый запуск** (файла нет): текущее состояние фиксируется как база, старые события
  не отправляются. Поэтому уже известный на момент включения `1.60.1.70532` не «обнаружится»
  задним числом, а ежедневный `OUTDATED` при `PRODUCT_BUNDLE` 70450 не будет присылать
  70532 каждый день — билд уведомляется один раз, следующий раз напишет только 70533+.
* **Недоставленное не подавляется и не теряется**: событие считается доставленным
  только после подтверждения (HTTP 200 `ok:true`). Все недоставленные кандидаты лежат
  в `candidate.json` как `pending` (список — новый кандидат не заменяет старого
  недоставленного) и повторяются каждым следующим запуском, включая обычный тихий
  `NO_ACTION`/`EXISTS`. Отпечаток сбоя этапа записывается только после фактической
  доставки алерта — пока алерт не ушёл, сломанный этап повторяет его. При частичной
  доставке подтверждается только доставленное (уходит из повторов), недоставленное
  остаётся; после успешной доставки повторов нет. Свежий `PREPARED` того же релиза
  обновляет факты (ссылку на PR), не удваивая сообщение.
* **Сбои** дедуплицируются на этап (`freshness/check`, `ota-prepare/prepare`, …):
  повторяющийся ежедневно сбой молчит, пока этап не восстановится (успешный запуск
  снимает отпечаток) — новый эпизод сообщится снова.
* **Доставка at-least-once, не exactly-once**: событие считается отправленным только
  после HTTP 200 `ok:true`; при неоднозначном сетевом ответе (таймаут после повторов)
  состояние не записывается, и следующий запуск может прислать сообщение повторно —
  в том числе если первое на самом деле дошло.

## Зависимости

Все уведомляющие джобы (и локальная инструкция выше) ставят одно и то же:
`pip install -e ".[ota]"`. Extra `ota` (cryptography) обязателен — импорт-цепочка CLI
включает строгую читалку `ota-prepare-report` (`talent_data.prepare.propose`), которая
зависит от неё; на чистом venv с `pip install -e .` импорт падает (проверено).

## Сбой Telegram — не сбой подготовки

Job `notify` в `dataset-freshness.yml` и `ota-prepare.yml` — `continue-on-error`: исход
проверки/подготовки/публикации он изменить не может. Своё состояние отправки он показывает
в summary запуска: `SENT (n)` / `нет событий` / `FAILED` / `SKIPPED`. Ограниченные
повторы: до 3 попыток; HTTP 429 уважается через `parameters.retry_after` (сон не дольше
30 с, иначе отказ); 5xx и транспортные ошибки — повтор с паузой 2 с; окончательные 4xx —
без повтора.

## Настройка (один раз)

1. **Бот.** В Telegram у [@BotFather](https://t.me/BotFather): `/newbot` → получите токен
   вида `123456:AA…`. Никому его не показывайте.
2. **Разрешение на личные сообщения.** Откройте диалог с новым ботом и отправьте ему
   `/start` (без этого бот не может писать вам первым).
3. **Выбор чата-получателя** — локальный помощник со своего компьютера:

   ```bash
   pip install -e ".[ota]" && TELEGRAM_BOT_TOKEN=123456:AA… python scripts/telegram_setup.py
   ```

   Он покажет кандидатов **личных** чатов (кто недавно писал боту) и попросит явно
   выбрать номер. Никакой автоматической отправки первому найденному чату нет;
   проверочное сообщение уходит только после явного «y» на вопрос (по умолчанию — нет).
   Помощник напечатает `TELEGRAM_CHAT_ID = <число>`.
4. **GitHub Environment.** Репозиторий → Settings → Environments → New environment →
   имя **`notifications`** (без required reviewers). Вкладка Environment secrets, добавить:
   * `TELEGRAM_BOT_TOKEN` — токен из шага 1;
   * `TELEGRAM_CHAT_ID` — число из шага 3.

   Рекомендуемая защита: в настройках окружения Deployment branches and tags →
   Restricted to `main` — тогда секреты окружения недоступны запускам с иных ref
   (включая `refs/pull/*/merge`), т.е. только коду `main`.
5. **Smoke-test.** Actions → **Telegram smoke test** → Run workflow. Должен прийти
   тестовое сообщение, summary — `SENT`. Без секретов запуск закончится явным `SKIPPED`
   в summary (это не ошибка).

Пока секреты не настроены, все уведомляющие джобы просто пишут `SKIPPED` в summary и
ничего не меняют.

## Безопасность токена

* Секреты объявлены только в jobs с `environment: notifications`. Все эти workflows
  запускаются исключительно событиями main: schedule, workflow_run, workflow_dispatch —
  код pull-request'ов их не исполняет, а ограничения веток окружения (шаг 4) закрывают
  вопрос окончательно.
* Токен передаётся только через переменные окружения; URL `api.telegram.org/bot<token>/…`
  строится внутри клиента и никогда не логируется: тексты ошибок собираются из имени
  метода, HTTP-кода и `description` Telegram, и дополнительно вырезают токен из любого
  текста (`redact`). Артефактов уведомления не создают.
* `GITHUB_TOKEN` для ветки состояния ходит в git через env-header (как `actions/checkout`),
  не через URL.

## Тесты

`tests/unit/test_telegram_notify.py`, `tests/unit/test_telegram_setup.py` (офлайн, без
реальных отправок): клиент против `httpx.MockTransport` (200, 429 с `retry_after`, 5xx,
транспортные ошибки, окончательные 4xx, не-JSON), отсутствие токена в любых сообщениях
об ошибках; все решения дедупликации (включая «70532 ежедневно — молчание», первый запуск,
восстановление после сбоя, переподпись ≠ выпуск, неверный/чужой каталог через
тестовый origin с TEST-ключами); свойства workflows (секреты только в environment-джобах
main-only, `continue-on-error` уведомляющих джобов, сценарий `Record the outcome` на
каждую комбинацию) и помощник настройки (список кандидатов, явный выбор, отсутствие
автоотправки).
