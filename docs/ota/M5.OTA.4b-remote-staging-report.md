* **Wire contract v1: unchanged.** No schema, model, fixture, conformance case or archive format.

  live origin, one phase per catalog state, with request / byte / connection / handshake counts.

## 7. Performance (ADR-0002, real HTTPS, JVM client)

Release B: 397 files, 5 077 048 bytes decoded; a cold install is 399 requests. The JVM fetcher sends
no `Accept-Encoding`, so these are identity bytes (5 154 313 on the wire = decoded files + manifest +
catalog); a gzip-capable client (Android) receives ≈ 2.35 MB for the same install (§3). Network:
the test Mac's Wi-Fi to `ru-msk`, ≈ 140 ms RTT. Three runs each.

| Case | Parallelism | Median | Range | Requests | Connections = TLS handshakes |
| --- | --- | --- | --- | --- | --- |
| cold | 4 | **25.7 s** | 25.2–27.4 | 399 | 4 |
| cold | 8 | **17.0 s** | 14.5–17.6 | 399 | 8 |
| warm (A installed, 6 files reusable) | 4 | **29.6 s** | 27.8–34.3 | 393 | 5–7 |
| warm | 8 | **19.0 s** | 18.2–19.6 | 393 | 8 |
| resume (interrupted at 50 %) | 4 | **15.7 s** | 13.5–18.5 | 205 | 4 |
| resume | 8 | **8.2 s** | 8.1–8.3 | 208–209 | 8 |

* **Request overhead:** on a kept-alive connection 96 % of a blob request's time is waiting for the
  first byte (19 blobs, 0.212 s of 0.222 s on average): delivery is latency-bound, so parallelism
  pays almost linearly and compression hardly changes the time on this link.
* **Connections / TLS:** one handshake per connection, connections kept alive for the whole
  install; parallelism 8 opens 8, never more (no churn against the JDK's 5-idle keep-alive cache
  while every slot stays busy). A cold TLS handshake to VK costs ≈ 0.3 s.
* **Warm** gains nothing: only 6 files are byte-identical between A and B (icons re-encoded, OD-6).
* **Reliability, not speed, is the open risk:** the connection stalls of §3 hit 3 of 7 attempts in
  the A phase and none of 19 in the B phase. Each costs an attempt (up to the 30 s read timeout) and
  is completed by the next check. Parallelism 8 opens more connections per install, so it is more
  exposed per attempt; the remedy is in the client's error handling, not in the parallelism (§9).

**Decision:** `DEFAULT_PARALLELISM = 8` — 34 % faster cold, 36 % warm, 48 % resume, measured over
real HTTPS; ADR-0002 is accepted with these numbers.

## 9. Known limitations and findings

* **VK connection stalls** (§3, §5.1): 7–11 % of new connections not accepted from the test network;
  a stalled request fails the whole client attempt after the read timeout, and the next trigger
  resumes. Suggested follow-up (client, no contract change): retry a file once or twice on a
  transient network failure inside an attempt, and a shorter connect timeout; ask VK support whether
  95.163.53.117 drops SYNs; consider a CDN in front for production (OD-1).
* **No concurrency protection from the store** (conditional writes ignored): single-publisher
  procedure (runbook §6.3).
* **The bucket host is VK's.** Moving providers changes the base URL compiled into builds; a
  project-owned hostname is still an OD-1 item for production.
* **Plain `http://` is served** by the origin; harmless for the app (refused client-side) but a
  production origin should refuse it at the edge — not redirect the HTTPS paths, which the client
  would refuse.
* **Device downloads stay small** while every published build is bundled.
* The 4a duplicate cold-start catalog GET and the About privacy copy (OD-4) are unchanged.
* `rollback`/`resign` print "sign the PAE with the production key" for the staging channel too
  (wording only).
