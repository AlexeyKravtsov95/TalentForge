# M5.OTA.4c — per-request retry, re-measured against VK staging

The client now repeats a GET whose transfer did not complete twice (0.5 s, 2 s) inside one
attempt, with a 10 s connect timeout on Android/JVM (client design §4.2). This report measures
that change against the real remote staging origin of M5.OTA.4b, in read-only mode, and compares
it with the M5.OTA.4b client and with the M5.OTA.4b findings.

## 1. Setup

* **Origin:** `https://talentforge-ota-staging.hb.ru-msk.vkcloud-storage.ru` (VK Cloud Object
  Storage, one address 95.163.53.117). **Read-only:** the client only sends GETs. No bucket
  object, catalog, key or configuration was created, changed or deleted. Only the public keyring
  (`staging-keyring.json`, key `tf-staging-2026`) was read; the private key was not used.
* **Live catalog during the runs:** staging, sequence 7, active `1.60.1.70450-r1` (B: 397 files,
  5 077 048 bytes decoded), valid until 2026-12-02.
* **Client:** the production stack on the desktop JVM. That means `OtaConfig.resolve` of the
  staging settings, `PlatformBlobFetcher` with the platform TLS roots (identity bytes, no
  `Accept-Encoding`), `java.security` signatures, the `java.nio` store and the system clock. Only
  build 70009 is bundled, so every file of B comes over the network: a cold install is 399 GETs
  (catalog, manifest, 397 blobs). **Parallelism 8.**
* **Network:** the test Mac (macOS 26.3.1) on Wi-Fi to `ru-msk`, ≈ 145 ms TCP connect (median of
  100).
* **Harness:** `OtaRetryRemoteMeasurement` (desktopTest, opt-in, §6). It runs two arms,
  interleaved run by run so both meet the same network:

  | Arm | Retry of a failed transfer | Connect timeout | Read timeout |
  | --- | --- | --- | --- |
  | `retry` (this PR) | 2 repeats, 0.5 s and 2 s | 10 s | 30 s |
  | `control` (the M5.OTA.4b client) | none | 15 s | 30 s |

  Every run is a cold install into a fresh directory. If the first check fails, a second check
  follows on the same directory (the app's next trigger). Every HTTP try is recorded **below** the
  retry, so a single failed try and a failed install are counted separately.

## 4. Run 2 — M5.OTA.4b's connection loss, injected (15:59–16:10 UTC, 20 cold installs per arm)

To measure the retry when the loss *does* happen, the harness injects it: with probability
q = 0.002, a try is a connection the origin never accepts. Such a try waits the arm's connect
timeout and returns `NetworkError(SocketTimeoutException)` without reaching the network; every
other try is real HTTPS to VK.

q = 0.002 is ≈ 0.8 lost connections per 399-try install, i.e. 10 % of the ≈ 8 connections of an
install (M5.OTA.4b: 7–11 % of new connections). The draws are seeded by the run, so both arms
meet the same sequence.

Injecting at the TLS socket instead does **not** work: `HttpURLConnection` silently re-opens a
connection that fails while being layered. A trial run at that level showed 2 injected
connection losses and no failed try.

| Metric | retry | control |
| --- | --- | --- |
| installed by the first check | **20/20 (100 %)** | **11/20 (55 %)** |
| installs needing a second check | 0 | 9 (all completed by it) |
| installs not completed after two checks | 0 | 0 |
| failed HTTP tries, all injected (real: 0) | 14 | 10 |
| retried tries (total / installs with ≥ 1 / max per install) | **14 / 9 / 4** | 0 (no retry) |
| retries that failed again | 0 | — |
| first check: median / p90 / worst | 14.3 s / 21.6 s / 25.5 s | 15.9 s / 19.6 s / 25.6 s |
| first check, installs with no loss: median | 13.4 s | 12.8 s |
| a failed first check / the second check that completed it | — | 16.5–25.6 s / 0.8–1.9 s |
| TLS connections per install: median / max | 9 / 19 | 8 / 19 |

* **Retry arm.** Every lost connection was retried and the repeat succeeded first time. An
  install never needed a second try of the same retry. The cost is the connect timeout (10 s)
  plus 0.5 s per lost try, overlapped with the other 7 downloads: +1 to +12 s on the affected
  installs. The worst case, 25.5 s, was the install that lost 4 connections.
* **Control arm.** Any single lost try ended the attempt after 15 s, with
  `Failed(Network(SocketTimeoutException))`, as in M5.OTA.4b. The verified files stayed staged,
  and the second check completed the install in ≈ 1 s.

**What "time to installed" means in the app.** For the control arm, the second check is not
immediate: it is the app's next trigger. That is the next return to the foreground when it is due
(6 h after the last successful check), the manual check, or the automatic backoff of 1 h after a
failure. So a failed first check delays the new data by up to an hour, or until the user returns.
The retry arm removes that delay for every install in this run.

## 6. Reproduce

```bash
cd mobile
./gradlew :composeApp:desktopTest --tests "*OtaRetryRemoteMeasurement*" \
    -Dtalentforge.ota.retrymeasure=<out dir> \
    -Dtalentforge.ota.retrymeasure.baseUrl=https://talentforge-ota-staging.hb.ru-msk.vkcloud-storage.ru \
    -Dtalentforge.ota.retrymeasure.keyring=<staging-keyring.json> \
    -Dtalentforge.ota.retrymeasure.runs=30            # run 1
# run 2: add -Dtalentforge.ota.retrymeasure.runs=20 -Dtalentforge.ota.retrymeasure.injectTryLoss=0.002
```

Outputs:

* `<out>/installs.tsv`: one row per check (time, tries, failed and retried tries, timeouts by
  kind, TLS connections, injected losses).
* `<out>/errors.tsv`: one row per failed try (object, offset, duration, kind, whether it was
  retried).
* `<out>/summary.md`.

Without `-Dtalentforge.ota.retrymeasure` the test is skipped.

## 7. Remaining failures and limitations

* **No real failure was observed**, in either arm, in 60 + 40 installs (≈ 40 000 GETs). The
  retry's effect on VK's own loss is therefore measured with injected loss (run 2), not with loss
  that occurred on its own. Run 1 confirms the retry costs nothing when nothing fails.
* **Only connection loss is injected.** A stall *after* the connection is accepted (TLS
  handshake or body never answered; M5.OTA.4b's 4 logged cases) would cost the 30 s read timeout
  per try instead of 10 s. The retry handles it the same way; at most 3 × 30 s + 2.5 s per file.
* **Repeats share the loss rate.** With independent losses at 10 % per connection, a file fails
  three times in a row with probability ≈ 0.1 %. Run 2 saw none in 14 retries.
* **The JVM client was measured**, not Android or iOS. Android uses the same `PlatformBlobFetcher`
  with gzip (smaller bodies, same request count). iOS gets the retry from common code but keeps
  its NSURLSession timeouts.
* GitHub Actions is still blocked by billing (M5.OTA.4b §10); every check was run locally.
