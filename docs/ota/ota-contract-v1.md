# OTA dataset delivery — contract v1 (M5.OTA.1)

Status: **proposed** (architecture milestone; nothing is published and no client exists yet).
Decision record: [ADR-0001](ADR-0001-remote-dataset-delivery.md).

This document specifies the wire contract between the TalentForge **publisher** (M5.OTA.2)
and the **mobile app** (M5.OTA.3). Either side can be built from this document alone.

The contract is **data only**. Nothing delivered over the air is executed, interpreted as
code, or used to change app behaviour beyond the existing strictly parsed data contracts.

Normative words: MUST, MUST NOT, SHOULD, MAY (RFC 2119 sense).

## 1. Storage layout

Everything is served by a static HTTPS origin (object storage behind a CDN). No server
logic, no REST API, no query parameters, no authentication.

```
<base>/v1/channels/production/catalog.json   mutable   ota-envelope.v1 carrying ota-catalog.v1
<base>/v1/channels/staging/catalog.json      mutable   ota-envelope.v1 carrying ota-catalog.v1
<base>/v1/blobs/sha256/<64 lowercase hex>    immutable any file, addressed by the SHA-256 of its bytes
```

* `<base>` is compiled into the app per channel (§8). It is **never** read from a
  downloaded document, so a document cannot redirect the client to another host.
* The catalog is the **only** mutable object. Release manifests, talent documents,
  sidecars and icons are all blobs.
* A blob's name is the SHA-256 of its exact bytes. A blob is never overwritten, and never
  deleted while any catalog of any channel lists a release that references it (§7.5).
* Both channels share one blob namespace: promoting a release from staging to production
  copies nothing.
* Recommended cache headers (the publisher sets them; the client does not rely on them):
  * blobs: `Cache-Control: public, max-age=31536000, immutable`;
  * catalog: `Cache-Control: public, max-age=300` (or lower).
* HTTP content encoding (gzip, br) is transport only. Every hash and length in this
  contract is over the **decoded** response body, i.e. the file bytes.

## 2. Common rules

These rules apply to every document of this contract:

1. **Encoding.** UTF-8 JSON (RFC 8259) without a byte order mark. One top-level object.
2. **Closed objects.** Unknown members MUST be rejected. Missing members MUST be rejected.
   No member has a default; even constants such as `schemaVersion` are on the wire.
3. **Unique keys.** An object that repeats a member name MUST be rejected — at any nesting
   depth, whatever the two values are (equal or not), in whichever order, and comparing names
   **after** unescaping (`"activeReleaseId"` and `"activeRelease\u0049d"` are the same name).
   This applies to the envelope, the catalog payload, the release manifest and every JSON
   content file of a release. Many JSON libraries silently keep the last value; see §2.1 for
   what a conforming implementation must do. Fixtures: `catalog-envelope-duplicate-key`,
   `catalog-envelope-nested-duplicate-key`, `catalog-duplicate-json-key`,
   `catalog-duplicate-key-same-value`, `catalog-duplicate-nested-key`,
   `catalog-duplicate-escaped-key`, `release-duplicate-nested-key`,
   `release-content-duplicate-key`.
4. **Strict wire types.** A number given as a string (`"2"`), a float for an integer, `null`
   for a non-null member, `NaN`/`Infinity` — all rejected, never coerced.
5. **Closed enums.** Values outside an enum (`channel`, `role`) are rejected.
6. **Timestamps.** RFC 3339 instants with a zero UTC offset (the publisher writes
   `YYYY-MM-DDTHH:MM:SSZ`). A timestamp without an offset is rejected.
7. **Hashes.** `sha256:` followed by 64 lowercase hex digits, over the exact bytes.
8. **Client builds.** `a.b.c.d`, four non-negative decimal integers, compared numerically
   component by component (`1.60.1.70450` > `1.60.1.70374`).
9. **Release ids.** `<clientBuild>-r<revision>`, revision `1`..`999999` without leading zeros
   (e.g. `1.60.1.70450-r1`). Releases are ordered by (clientBuild, revision).
10. **Limits.** `catalog.json` at most **1 MiB** (1 048 576 bytes) as received; at most 4
    signatures, 512 catalog releases, 4096 files per release, 16 MiB per file and 256 MiB per
    release. A document over a limit is rejected, never truncated. The catalog limit is
    enforced **while reading the response** — the client stops reading after 1 MiB + 1 byte and
    reports `CATALOG_TOO_LARGE` without parsing anything (fixture `catalog-over-size-limit`).
    A maximal valid catalog (512 releases with the longest plausible ids and sizes, indented,
    4 signatures) is ≈ 230 KB, so the limit leaves more than 4× headroom
    (`test_a_maximal_valid_catalog_fits_the_size_limit`). The release manifest's bound is its
    pinned `manifestByteLength`; every other file's bound is its `byteLength`.

### 2.1 Duplicate member names: implementation requirement

Detection MUST happen on the raw JSON text, before any step that can lose a repeated name.
Parsing into a map-like structure (`JsonObject`, `dict`, `Map`) first and checking afterwards
is **not** sufficient: such structures keep one value per name, so the duplicate is already
gone. Equally, a typed decoder that assigns fields as it reads them may let the last value
win without an error; its behaviour on duplicates must never be assumed (M5.OTA.3 records it
in a test, but does not rely on it).

Conforming implementations:

* **Python reference:** `json.loads(..., object_pairs_hook=...)` receives every (name, value)
  pair of each object in source order, with names already unescaped, before a `dict` exists —
  `talent_data.ota.verify.strict_json`.
* **Kotlin client (M5.OTA.3):** kotlinx.serialization exposes no public token stream, and
  its `JsonObject` is a map. The client therefore runs a dedicated **duplicate-name scanner**
  over the UTF-8 bytes before decoding: a small lexer that tracks string tokens, `{`/`}`/`[`/`]`
  nesting and the name position inside each object, unescapes each member name (`\"`, `\\`,
  `\/`, `\b`, `\f`, `\n`, `\r`, `\t`, `\uXXXX` including surrogate pairs) and keeps one set of
  names per open object. It does not build values and is not a JSON parser; well-formedness and
  types are still checked by the strict decoder afterwards. It is required to be tested
  against every fixture above, against escaped and nested duplicates, and differentially
  against the Python reference on generated documents. No new library is added for this:
  the project's JSON library (kotlinx.serialization) has no public token stream, and a second
  JSON library only for duplicate detection is not justified when a scanner of this size,
  covered by fixture and differential tests, suffices. If M5.OTA.3 finds a maintained KMP
  library that exposes raw member names in source order on Android, iOS and the JVM, it may be
  used instead, recorded as a dependency decision in its PR.

The code a duplicate produces depends only on the stage (first failing check wins):

| Document | Code |
| --- | --- |
| envelope | `ENVELOPE_INVALID` |
| catalog payload | `PAYLOAD_INVALID` |
| release manifest | `MANIFEST_INVALID` |
| any JSON file of a release (dataset manifest, talent data, sidecars, registry, localization) | `CONTENT_INVALID` |

## 3. `ota-envelope.v1` — signed wrapper

```json
{
  "payloadType": "application/vnd.talentforge.ota-catalog.v1+json",
  "payload": "<standard base64 of the exact payload bytes>",
  "signatures": [
    { "keyId": "tf-prod-2026a", "sig": "<standard base64 of an ASN.1 DER ECDSA signature>" }
  ]
}
```

* `payload` — standard base64 (RFC 4648 §4) **with** padding and **no** whitespace or line
  breaks. Any other spelling of the same bytes is rejected, so a payload has exactly one
  encoding (fixture `catalog-envelope-noncanonical-base64`).
* `payloadType` — v1 defines exactly one: `application/vnd.talentforge.ota-catalog.v1+json`.
  It is part of the signed message (domain separation): a signature over a document of
  another type can never be replayed as a catalog (fixture `catalog-wrong-payload-type`).
* `signatures` — 1..4 entries, `keyId` unique within the envelope.
* **Signed message:** the DSSE v1 pre-authentication encoding
  ([DSSE protocol](https://github.com/secure-systems-lab/dsse/blob/master/protocol.md)):

  ```
  PAE(type, body) = "DSSEv1" SP LEN(type) SP type SP LEN(body) SP body
  ```

  `LEN` is the byte length in ASCII decimal without leading zeros; `SP` is one space
  (0x20); `type` is the UTF-8 `payloadType`; `body` is the decoded payload bytes.
  Example: `PAE("application/x", "hello") = "DSSEv1 13 application/x 5 hello"`.
* **Algorithm:** ECDSA over NIST P-256 with SHA-256 (`ecdsa-p256-sha256`; Android/JVM
  `SHA256withECDSA`, iOS `kSecKeyAlgorithmECDSASignatureMessageX962SHA256`). The signature
  is ASN.1 DER `SEQUENCE { r INTEGER, s INTEGER }` (the form both platforms produce and
  verify natively), base64-encoded.
* **Validity:** an envelope is authentic when **at least one** signature whose `keyId` is in
  the app's pinned keyring verifies over the PAE. Signatures by key ids the app does not
  pin are ignored (fixture `catalog-b-active-extra-unknown-signer`). The threshold is 1.
* The payload is parsed **only after** a signature verified, and exactly the verified bytes
  are parsed. Nothing is canonicalized or re-serialized before verification.

Only the catalog is signed. Everything else is authenticated by a hash chain that starts
at the signed catalog (§5, §6).

## 4. `ota-catalog.v1` — the channel's root of trust

Example (payload of fixture `catalog-b-active`, hashes shortened here):

```json
{
  "schemaVersion": 1,
  "game": "forever",
  "channel": "production",
  "sequence": 2,
  "issuedAt": "2026-10-18T00:00:00Z",
  "expiresAt": "2026-12-02T00:00:00Z",
  "activeReleaseId": "1.60.1.70450-r1",
  "releases": [
    {
      "releaseId": "1.60.1.70374-r1",
      "clientBuild": "1.60.1.70374",
      "minDataLevel": 1,
      "manifestSha256": "sha256:48ccbb16…25cdd",
      "manifestByteLength": 75599,
      "totalByteLength": 5000463,
      "publishedAt": "2026-10-17T23:30:00Z"
    },
    {
      "releaseId": "1.60.1.70450-r1",
      "clientBuild": "1.60.1.70450",
      "minDataLevel": 1,
      "manifestSha256": "sha256:c0091923…0c17f",
      "manifestByteLength": 75792,
      "totalByteLength": 5077048,
      "publishedAt": "2026-10-17T23:30:00Z"
    }
  ]
}
```

| Member | Meaning |
| --- | --- |
| `schemaVersion` | `1`. Any other integer: `UNSUPPORTED_SCHEMA_VERSION`. |
| `game` | Game key (`forever`); must equal the app's game. |
| `channel` | `production` or `staging`; must equal the channel the app reads. |
| `sequence` | Integer ≥ 1. Strictly greater for every new catalog of the channel. |
| `issuedAt`, `expiresAt` | Validity window: `issuedAt < expiresAt ≤ issuedAt + 180 days`. |
| `activeReleaseId` | The release new builds should be created on. Must be listed. |
| `releases` | Every retained release, ordered by (clientBuild, revision), ids unique. |
| `releases[].releaseId` | `<clientBuild>-r<revision>`; must start with its own `clientBuild`. |
| `releases[].minDataLevel` | Lowest app data level (§9) that can use the release. |
| `releases[].manifestSha256`, `manifestByteLength` | Pin of the release manifest blob. |
| `releases[].totalByteLength` | Sum of the release's file sizes (equals the manifest's). |
| `releases[].publishedAt` | When the release was first listed (informational). |

Publisher obligations (verified by the publisher's own tests in M5.OTA.2; not all can be
checked by a client):

* **Append-only releases.** A release, once listed in a production catalog, stays listed
  in every later production catalog with identical members. Saved builds depend on it
  (§7). Removing one is an owner decision recorded in the release log
  ([OD-7](open-decisions.md)).
* **One talent dataset per client build.** All releases of one (game, clientBuild) carry
  identical talent data: the same dataset-manifest classes (token, file, treeIds,
  contentHash). Only presentation (visuals, icons, tooltips, localization) may differ
  between revisions. Clients enforce it against what they already trust (§6.4 #7,
  `BUILD_IDENTITY_CONFLICT`).
* **Monotonic sequence**, including rollbacks: a rollback is a **new** catalog with a
  higher `sequence` whose `activeReleaseId` names an older release.
* **Re-sign before expiry.** A catalog must be re-issued (same releases, new `sequence`,
  `issuedAt`, `expiresAt`) before `expiresAt`. A lapsed catalog is fail-safe: clients keep
  their current data and stop updating until a fresh catalog appears.

## 5. `ota-release.v1` — immutable release manifest

Example (start of `fixtures/v1/releases/1.60.1.70450-r1.release.json`, hashes shortened):

```json
{
  "schemaVersion": 1,
  "game": "forever",
  "clientBuild": "1.60.1.70450",
  "releaseId": "1.60.1.70450-r1",
  "minDataLevel": 1,
  "createdAt": "2026-10-17T23:00:00Z",
  "provenance": {
    "repositoryCommit": "c749ebc5fc31c43be742844cb89d012f100a2a0a",
    "validation": "talent-data validate + manifest + visuals/tooltips/localization sync checks"
  },
  "files": [
    {"path": "dataset/forever/1.60.1.70450/druid.json", "role": "TALENT_DATA", "sha256": "sha256:c7194d06…f08f", "byteLength": 115026},
    {"path": "dataset/forever/1.60.1.70450/manifest.json", "role": "DATASET_MANIFEST", "sha256": "sha256:5bbc3b76…9d68", "byteLength": 3338}
  ],
  "totalByteLength": 5077048
}
```

* `files` — ordered by `path` (byte order of the UTF-8 path), each path once.
* `files[].sha256` — the file's SHA-256 **and** its blob address
  (`v1/blobs/sha256/<hex>`). Two paths may share one blob.
* `totalByteLength` — exactly the sum of `files[].byteLength`; the client uses the catalog
  copy of it to check free space **before** downloading anything (§7.3).
* `provenance.repositoryCommit` — the TalentForge commit whose committed `data/` was
  published. It makes every release reproducible from the repository.
* The byte form of the manifest is free (indentation, member order): the catalog pins the
  bytes, and nothing is canonicalized.

### 5.1 Roles and paths

A release is a **complete** snapshot of one client build: everything the app reads for that
build, in exactly the layout the app already uses for its bundled resources
(`composeResources/files/…`). With `g` = `game` and `b` = `clientBuild` of the manifest:

| Role | Path (anchored) | Count | Content contract |
| --- | --- | --- | --- |
| `DATASET_MANIFEST` | `dataset/g/b/manifest.json` | exactly 1 | `dataset-manifest.v1` |
| `TALENT_DATA` | `dataset/g/b/<name>` | one per manifest class | `talent-data.v1` |
| `ICON_REGISTRY` | `visuals/g/b/icons.json` | exactly 1 | `talent-icons.v1` |
| `ICON_IMAGE` | `visuals/g/b/icons/[1-9][0-9]{0,9}.png` | one per registry icon | PNG |
| `VISUALS` | `visuals/g/b/<name>` | one per talent file | `talent-visuals.v1` |
| `TOOLTIPS` | `tooltips/g/b/<name>` | one per talent file | `talent-tooltips.v1` |
| `LOCALIZATION` | `localization/g/b/[a-z]{2}[A-Z]{2}/<name>` | per locale: one per talent file | `talent-localization.v1` |

`<name>` is `[a-z][a-z0-9_]{0,31}\.json`, excluding `manifest.json` (for `TALENT_DATA`) and
`icons.json` (for `VISUALS`). Paths therefore never contain `..`, a leading `/`, a
backslash, an empty segment or another build's directory: path traversal is impossible by
grammar (fixtures `release-path-traversal`, `release-path-of-other-build`). The exact
regular expressions are `role_path_pattern` in the reference verifier.

There is **no** role for code, scripts, configuration, URLs or UI. A release with any other
role is rejected (fixture `release-unknown-role`).

## 6. Verification algorithm

The client MUST perform these checks **in this order** and stop at the first failure with
the listed code. The order is part of the contract: the conformance suite pins the code
for objects that are wrong in several ways at once.

### 6.1 Catalog (`verify_catalog`)

| # | Check | Code |
| --- | --- | --- |
| 0 | Response is at most 1 MiB (checked while reading) | `CATALOG_TOO_LARGE` |
| 1 | Envelope is strict JSON (§2 incl. unique member names) matching `ota-envelope.v1`; `payload` and every `sig` are canonical base64; `keyId`s unique | `ENVELOPE_INVALID` |
| 2 | `payloadType` is the catalog type | `PAYLOAD_TYPE_MISMATCH` |
| 3 | At least one signature has a pinned `keyId` | `UNTRUSTED_SIGNER` |
| 4 | At least one pinned signature verifies over `PAE(payloadType, payload)` | `SIGNATURE_INVALID` |
| 5 | Payload is strict JSON (§2 incl. unique member names) | `PAYLOAD_INVALID` |
| 6 | Integer `schemaVersion` other than 1 | `UNSUPPORTED_SCHEMA_VERSION` |
| 7 | Payload matches `ota-catalog.v1`; UTC timestamps | `PAYLOAD_INVALID` |
| 8 | `game` equals the app's game | `GAME_MISMATCH` |
| 9 | `channel` equals the app's channel | `CHANNEL_MISMATCH` |
| 10 | `now < expiresAt` (device clock) | `CATALOG_EXPIRED` |
| 11 | `sequence ≥` last accepted; if equal, the payload SHA-256 equals the last accepted one | `SEQUENCE_REGRESSION` |
| 12 | Window positive and ≤ 180 days; release ids unique, each naming its `clientBuild`; ordered; `activeReleaseId` listed | `CATALOG_INCONSISTENT` |

On acceptance the client persists `{sequence, payloadSha256}` and the payload bytes of the
catalog (§7.2) **before** acting on it, so it never needs the network to look up a release
it has already seen.

### 6.2 Activation decision (`decide_activation`)

Given a verified catalog, the app's data level `L`, the app's bundled product build `P`
and the currently active OTA release `C` (none while the bundled product is in use), with
`A` the release named by `activeReleaseId`:

| Condition (first match) | Decision | Effect |
| --- | --- | --- |
| `A.minDataLevel > L` | `KEEP_CURRENT_INCOMPATIBLE` | nothing downloaded; the app may say "update the app for newer talent data" |
| `A.clientBuild < P` | `KEEP_BUNDLED_FLOOR` | nothing downloaded; the bundled product is the floor of every rollback |
| `A.releaseId == C` | `NO_CHANGE` | nothing downloaded |
| otherwise | `ACTIVATE` | install `A` (§6.3–6.4), then make it active (§7) |

The client activates **only** `activeReleaseId` — never "the newest release it can read".
A rollback is an `ACTIVATE` of an older release ([OD-3](open-decisions.md) records the
bundled-floor choice). After `KEEP_BUNDLED_FLOOR` the effective product is the bundled one
if no OTA release at or above `P` is active.

### 6.3 Release manifest (`verify_release_manifest`)

For the catalog entry `E` of the release being installed (from a verified catalog):

| # | Check | Code |
| --- | --- | --- |
| 1 | Byte length equals `E.manifestByteLength` and SHA-256 equals `E.manifestSha256` | `MANIFEST_HASH_MISMATCH` |
| 2 | Strict JSON (§2 incl. unique member names) | `MANIFEST_INVALID` |
| 3 | Integer `schemaVersion` other than 1 | `UNSUPPORTED_SCHEMA_VERSION` |
| 4 | Matches `ota-release.v1`; UTC timestamps | `MANIFEST_INVALID` |
| 5 | `game`, `clientBuild`, `releaseId`, `minDataLevel`, `totalByteLength` equal the app's game / `E` | `RELEASE_IDENTITY_MISMATCH` |
| 6 | `minDataLevel ≤ L` | `INCOMPATIBLE_DATA_LEVEL` |
| 7 | Paths unique; ordered; each path matches its role (§5.1); `totalByteLength` is the sum; exactly one `DATASET_MANIFEST` and `ICON_REGISTRY`; at least one `TALENT_DATA`, `VISUALS`, `TOOLTIPS`, `LOCALIZATION` | `LAYOUT_INVALID` |

### 6.4 Release files (`verify_release_files`)

Every file, in manifest order, then the snapshot as a whole:

| # | Check | Code |
| --- | --- | --- |
| 1 | File length equals `byteLength` (a short or long download) | `BLOB_SIZE_MISMATCH` |
| 2 | File SHA-256 equals `sha256` | `BLOB_HASH_MISMATCH` |
| 3 | Every JSON file is strict JSON (§2 incl. unique member names); dataset manifest: strict `dataset-manifest.v1`, `validation.errors == 0` for every class, no repeated file | `CONTENT_INVALID` |
| 4 | Dataset manifest `game` / `clientBuild` | `CONTENT_IDENTITY_MISMATCH` |
| 5 | `TALENT_DATA` files are exactly the manifest's class files | `RELEASE_INCOMPLETE` |
| 6 | Each talent document: strict `talent-data.v1`; game, build, class token, `contentHash`, tree ids equal its manifest entry | `CONTENT_INVALID` / `CONTENT_IDENTITY_MISMATCH` |
| 7 | Same-build identity: when the device already trusts a dataset of this (game, clientBuild) — bundled, or an installed release — the manifest classes (token, file, treeIds, contentHash) are identical | `BUILD_IDENTITY_CONFLICT` |
| 8 | Icon registry: strict `talent-icons.v1`, game/build; `ICON_IMAGE` files are exactly the registry's files, each with the registry's `sha256` and `byteLength`, each starting with the PNG signature | `RELEASE_INCOMPLETE` / `CONTENT_IDENTITY_MISMATCH` / `CONTENT_INVALID` |
| 9 | `VISUALS` and `TOOLTIPS`: one per talent file; strict; game, build, class token, `talentDataContentHash` equal the talent document; every visual's icon is registered | `RELEASE_INCOMPLETE` / `CONTENT_INVALID` / `CONTENT_IDENTITY_MISMATCH` |
| 10 | `LOCALIZATION`: each locale complete; strict; game, build, class, locale, `talentDataContentHash`, `tooltipsContentHash` | `RELEASE_INCOMPLETE` / `CONTENT_INVALID` / `CONTENT_IDENTITY_MISMATCH` |

After these checks pass, the M5.OTA.3 client **additionally** runs the staged release
through the app's own existing repositories (`BundledTalentDatasetRepository`, visuals,
tooltips, localization — including localization's own content-hash recomputation) for every
class. Any typed failure there rejects the release with `CONTENT_INVALID`. A release is
never activated on the strength of hashes alone.

### 6.5 Wire validity is not functional support

A release can be **valid on the wire** — it passes every check of §6 — and still contain a
mechanic the allocation engine cannot handle. Two cases:

1. **A value outside a closed contract** (unknown field, unknown prerequisite kind, new schema
   version): the strict readers reject it → `CONTENT_INVALID` / `UNSUPPORTED_SCHEMA_VERSION`
   (fixture `release-new-mechanic`). The client never sees it as data.
2. **A value inside an open union** of `talent-data.v1` (node `type`, raw entry types, node
   flags, unresolved conditions): preserved by the readers, and reported by the allocation
   engine as fail-closed (`UNSUPPORTED_NODE_TYPE`, `UNSUPPORTED_ENTRY_TYPE`,
   `UNSUPPORTED_NODE_FLAGS`, `UNSUPPORTED_EDGE_COMBINATION`, `UNRESOLVED_CONDITION`,
   `NODE_NEVER_PURCHASABLE`). Such a release is **wire-valid** (fixture
   `release-open-union-node-type`), so the client verifier cannot be the protection.

The protection is a **publication rule**, enforced by the publisher (gate G6,
[publisher-and-security.md](publisher-and-security.md) §2.1) and executable today as
`talent_data.ota.mechanics.new_unsupported_mechanics`:

* Each data level `L` has a frozen **baseline** of known, investigated fail-closed findings
  (`docs/ota/data-levels/level-<L>.json`, §9). For level 1 it is exactly one finding: Rogue
  Venom (tree 1111, node 105712, `UNRESOLVED_CONDITION` 50984), present in every bundled build
  and documented as COND-1 in `docs/talent-allocation-semantics.md`.
* A release whose engine findings are not all in the baseline of its `minDataLevel` is a
  **STOP** for production. No approval record, flag or option can override it — owner approval
  cannot substitute for engine support. (Staging may carry a release for a level that has no
  baseline yet only while an app build implementing that level is being developed and tested;
  it cannot be promoted until the level exists.)
* A new mechanic therefore needs, in order: (1) an app release whose engine supports it (or that
  ships it as a newly investigated, documented fail-closed anomaly, with evidence per the
  semantics document); (2) a new data level `L+1` whose baseline is generated from what that app
  was tested with; (3) only then a release with `minDataLevel = L+1`. Apps below `L+1` never
  download it (§6.2 `KEEP_CURRENT_INCOMPATIBLE`, §6.3 `INCOMPATIBLE_DATA_LEVEL`).
* New **warnings** that do not change what the engine supports are a different matter: they may
  pass after manual review (gate G5). A finding of G6 is never accepted through G5.

## 7. Client state, atomicity and retention (normative summary)

The full design is in [client-architecture.md](client-architecture.md); these rules are the
contract-relevant part.

### 7.1 Atomic installation

1. Download into `staging/<releaseId>/` — at most one staging directory per release id, never
   read as a release and never made active.
2. Verify per §6.3–6.4 and the app's repositories.
3. Write the verified release manifest into the staging directory, then **rename** the
   staging directory to `releases/<releaseId>` (one atomic rename on one volume).
4. Activate by atomically replacing the state file (§7.2): write a temporary file, flush it
   to disk, rename it over the old one.

A crash at any point leaves either the old state or the new one, never a mixture. The active
dataset changes only in step 4, after the whole release has been verified.

### 7.2 Persisted state

The client persists (format is the client's choice, written atomically):

* the last accepted catalog: `sequence`, payload SHA-256 and payload bytes;
* the active release id (absent = bundled product);
* the previous active release id (the one-step local fallback);
* the installed releases and the SHA-256 of each one's manifest.
* the releases rejected for their content, with manifest SHA-256 and code — never retried
  for the same bytes (transient failures, including a blob that arrived corrupt, are retried).

An unreadable state file is treated as "no OTA state": the app uses its bundled data, keeps
every installed release on disk untouched, and the next valid catalog rebuilds the state.
It is never treated as permission to delete anything.

### 7.3 Downloads and resume

* A file is downloaded to `<path>.part` and renamed to `<path>` inside the staging directory
  only after its length and SHA-256 match the manifest. A `.part` file is never reused.
* Before the first byte of an attempt, the client checks free space ≥ (sum of `byteLength`
  of the files still missing) + 10 MiB.
* A file needed by the release that is already present locally with the right hash — in the
  staging directory, in another installed release, or among the app's bundled resources — is
  reused, not downloaded. **Reuse always re-reads the file and re-checks its length and
  SHA-256 against the manifest being installed**; no local marker, timestamp or bookkeeping
  file is trusted as proof that a file is valid. A file that fails the check is deleted and
  acquired again.
* `staging/<releaseId>/attempt.json` records `releaseId`, `manifestSha256`,
  `manifestByteLength` and the attempt's timestamps. When the attempt resumes and the
  verified catalog pins **different** manifest bytes for that release id (a violation of the
  append-only rule, or corrupted local data), the whole staging directory is deleted and the
  attempt starts again from nothing.
* Insufficient space (before the attempt, or `ENOSPC` while writing): the attempt ends with
  "insufficient storage", the `.part` file being written is deleted, verified staged files are
  kept for a later resume — unless free space is below the 10 MiB margin itself, in which case
  the staging directory is deleted so the app does not hold the device's last free space.

### 7.4 Recovery at startup

`recover()` runs before the first screen, without the network, and:

* deletes `state.json.tmp`, every `*.part` file, and `trash/`;
* keeps every staging directory, **except** ones that are safely garbage: a name that is not a
  valid release id, a missing or unreadable `attempt.json`, an `attempt.json` naming another
  release id, or a release id that is already installed with the same manifest SHA-256;
* never deletes, moves or reads from staging a file of an installed release, and never makes a
  staging directory active;
* never deletes an installed release (a broken active release is moved to `quarantine/`, see
  the client design), so releases used by saved builds or open sessions are untouched.

Staging directories that are merely **stale** are deleted later, by retention after a
successful catalog check ([client design §5.3](client-architecture.md)), when the client can tell: the release is no longer listed or
no longer wanted (neither active, nor needed by a saved build, nor requested on demand), or
the attempt has not progressed for 30 days.

### 7.5 What may never be deleted

* Server side: no listed release, no blob referenced by a listed release.
* Client side: the active release; the previous release; every release whose client build
  is referenced by a saved build; any release used by an open editor session. If the
  saved-build library cannot be read, no installed release is deleted (only stale staging,
  quarantine and trash may be). Staging directories are deleted only under §7.3 and §7.4.

## 8. Keys and channels

* An app build pins **one channel** (`production` for store builds, `staging` for internal
  builds) together with that channel's `<base>` URL and keyring. A catalog for another
  channel is rejected (`CHANNEL_MISMATCH`), so a staging catalog never reaches production
  users even if it is copied to the production path.
* Keyring entry: `{keyId, algorithm: "ecdsa-p256-sha256", publicKeySpki}` — the public key
  as base64 DER `SubjectPublicKeyInfo` (Android `X509EncodedKeySpec`; on iOS the last 65
  bytes of the 91-byte P-256 SPKI are the X9.63 point `SecKeyCreateWithData` expects).
* Production apps pin **two** production keys from day one: the primary signing key and an
  offline backup key (fixture `catalog-b-active-backup-key`). Losing the primary key does
  not require an app update. Key handling: [publisher-and-security.md](publisher-and-security.md).
* `keyId` values starting with `test-` are reserved for fixtures. An app keyring MUST NOT
  contain one; M5.OTA.3 adds a test for that.

## 9. Data levels

`minDataLevel` is a single integer that summarizes "which contracts and semantics the app
must implement to use this release". An app declares the highest level it supports.

| Level | Meaning |
| --- | --- |
| 1 | `dataset-manifest.v1`, `talent-data.v1`, `talent-visuals.v1`, `talent-icons.v1`, `talent-tooltips.v1`, `talent-localization.v1` (`ruRU`) as implemented by the app at M5.OTA.3, with the allocation semantics of `docs/talent-allocation-semantics.md` at that time. |

A new level is defined only together with an app release that implements it. The publisher
sets the lowest level that can correctly read **and interpret** the release.

Every level has a baseline file, `docs/ota/data-levels/level-<L>.json`, listing the engine's
fail-closed findings that apps of that level are known to handle (as unsupported, visibly
fail-closed nodes): class token, tree id, node id, entry id, issue code, condition id, and the
evidence. The baseline is frozen when the first app implementing the level ships; it is never
extended afterwards — a new finding needs a new level. Level 1's baseline is generated from, and
tested against, the five bundled builds (`tests/unit/ota/test_ota_mechanics_gate.py`). The
baseline is publisher-side policy data, not part of the wire contract; clients only see
`minDataLevel`.

## 10. Versioning of this contract

* Any change to a document's shape is a new version of that document (a new `payloadType`
  for the catalog, a new `schemaVersion` for the release manifest). A v1 app rejects a newer
  document with `PAYLOAD_TYPE_MISMATCH` / `UNSUPPORTED_SCHEMA_VERSION` and keeps its data.
* A layout change that old apps would misread uses a new storage prefix (`v2/`); the
  publisher keeps serving `v1/` for as long as installed apps read it ([OD-9](open-decisions.md)).
* A new optional member is **not** backward compatible under §2 rule 2; it is a new version.

## 11. Error codes

| Code | Stage | Typical cause |
| --- | --- | --- |
| `CATALOG_TOO_LARGE` | catalog | response over 1 MiB (misconfigured origin, hostile response) |
| `ENVELOPE_INVALID` | catalog | truncated download, wrong shape, non-canonical base64, duplicate keyId or member name |
| `PAYLOAD_TYPE_MISMATCH` | catalog | a signed document of another type |
| `UNTRUSTED_SIGNER` | catalog | signed only by unknown keys |
| `SIGNATURE_INVALID` | catalog | tampering, wrong key |
| `PAYLOAD_INVALID` | catalog | strict JSON/schema violation |
| `UNSUPPORTED_SCHEMA_VERSION` | catalog, release | a newer contract |
| `GAME_MISMATCH`, `CHANNEL_MISMATCH` | catalog | wrong file at the URL |
| `CATALOG_EXPIRED` | catalog | stale CDN copy, freeze attack, lapsed re-signing |
| `SEQUENCE_REGRESSION` | catalog | replay of an older catalog, equivocation |
| `CATALOG_INCONSISTENT` | catalog | publisher defect |
| `MANIFEST_HASH_MISMATCH` | release | truncated or replaced manifest |
| `MANIFEST_INVALID` | release | strict JSON/schema violation, unknown role |
| `RELEASE_IDENTITY_MISMATCH` | release | manifest does not match its catalog entry |
| `INCOMPATIBLE_DATA_LEVEL` | release | release for a newer app |
| `LAYOUT_INVALID` | release | path/role/size violation |
| `BLOB_SIZE_MISMATCH`, `BLOB_HASH_MISMATCH` | files | partial or corrupt download |
| `CONTENT_INVALID` | files | strict content contract violation, failed app validation |
| `CONTENT_IDENTITY_MISMATCH` | files | documents of different builds/classes mixed |
| `RELEASE_INCOMPLETE` | files | a required file is missing |
| `BUILD_IDENTITY_CONFLICT` | files | different talent data for an already trusted client build |

Client-only conditions that are not contract verdicts (no fixture): network unavailable,
HTTP status other than 200, insufficient storage, local I/O failure, cancelled attempt.

**Every** failure above has the same effect on the device: the attempt is abandoned, the
active dataset and the saved-build library are untouched, and the next attempt happens no
earlier than the normal check interval.

## 12. Conformance suite

`docs/ota/fixtures/v1/`:

| Path | Content |
| --- | --- |
| `keyring.json` | the two pinned TEST keys (`test-primary`, `test-backup`) and one untrusted key |
| `catalogs/*.json` | 39 catalog envelopes (8 accepted, 31 rejected) |
| `releases/*.release.json` | the real releases A = `1.60.1.70374-r1`, B = `1.60.1.70450-r1`, and B-r2 (data level 2) |
| `releases/invalid/`, `releases/edge/` | corrupted and edge-case release manifests |
| `blobs/` | file contents that differ from the repository (corrupt icons, modified documents) |
| `cases.json` | all 64 cases (39 catalog, 25 release): input, context, expected verdict |

A release case's `files.source = "repository"` means: read each release path from the
committed data (`dataset/…` → `data/normalized/…`, `visuals/…` → `data/visuals/…`,
`tooltips/…` → `data/tooltips/…`, `localization/…` → `data/localization/…`), except paths
listed in `files.overrides`, whose value is either a fixture path (`blobs/…`) or
`repository:<release path>`. `knownSameBuildManifest: "repository"` means the committed
dataset manifest of the same build is the one the device already trusts.

The TEST private keys are derived from public seeds in the generator. Anyone can sign with
them, which is the point: they exist only to make signatures reproducible.
`tests/unit/ota/test_ota_contract.py` replays every case with the reference verifier,
checks that every error code and activation decision is exercised, and that a regeneration
is byte-identical.
