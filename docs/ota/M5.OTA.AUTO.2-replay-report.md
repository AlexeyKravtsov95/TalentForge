# M5.OTA.AUTO.2 — Historical Patch Replay + Staging E2E: отчёт

Воспроизводимый end-to-end прогон обновления игровых данных WoW: Forever на реальных исторических
сборках, без ожидания нового патча:

**обнаружение патча → подготовка данных → валидация → staging-публикация → загрузка клиентом →
активация нового датасета.**

* Исходная сборка: `1.60.1.70374`. Новая сборка: `1.60.1.70450`.
* Production OTA, production-ключи, production S3 и `ota.mythweld.com` не изменялись. Production
  только читался: два анонимных GET каталога до и после прогона.
* `PRODUCT_BUNDLE` (70450) и release-конфигурация приложения не менялись. Историческое приложение
  «до патча» собиралось только в тестах и в одноразовом worktree (§7).

## 4. Что реально загрузилось по сети

Источник: evidence `OtaHistoricalReplayTest` (`<out>/client/theClientMovesFrom70374To70450.json`)
и журнал origin. Релиз 70450-r1 содержит 397 файлов (5 077 048 байт).

| Откуда | Файлов | Что |
| --- | --- | --- |
| **HTTPS (staging origin)** | **391** + манифест; 392 blob-запроса, **5 042 736 байт** файлов | `dataset` 10 (9 классов + manifest), `tooltips` 9, `localization` 9, `visuals` 363 |
| установленный релиз 70374 (кэш клиента, тот же SHA-256) | 6 | иконки `132198`, `135957`, `135959`, `136006`, `136218`, `252996` |
| bundle приложения | 0 | 70450 не бандлится; ни одного чтения пути 70450 из bundle |

Тест требует, чтобы множество запрошенных blob-ов **в точности** совпадало с файлами, которых нет
у установленного 70374 (плюс манифест). Число загруженных и скопированных файлов сверяется с
отчётом установки клиента. Сам 70374-r1 ставится из bundle: по сети приходит только его манифест.

## 5. Подпись и целостность

* Каталог: ECDSA P-256 (`ota-envelope.v1`), ключ `tf-staging-local-*` из keyring стенда. Клиент
  проверяет его через `java.security`, Python — эталонным `verify_catalog`. Production keyring
  этот каталог отвергает, а production-конфигурация клиента отказывается от staging-ключа
  (`KEY_NOT_FOR_CHANNEL`, `OtaStagingE2ETest.theThreeKeyClassesStaySeparated`).
* Манифест: байты на устройстве равны байтам publisher, SHA-256 закреплён в подписанном каталоге.
* Файлы: каждый из 397 установленных файлов перехеширован на диске клиента и равен пину манифеста.
  Те же 397 файлов совпадают с подготовленным кандидатом (S2) и с релизом из main (P7).
* Подмена каталога, манифеста или файла отвергается типизированной ошибкой и ничего не меняет (N1, N2).

## 7. Процедура: эмулятор и физическое Android-устройство

Обычный APK для этой проверки не подходит: он бандлит 70450 как `PRODUCT_BUNDLE` и только копирует
его файлы из bundle ([android-device-smoke.md](android-device-smoke.md) §2). Нужен
**исторический debug-APK**. Он собирается локально в одноразовом worktree и никогда не
коммитится и не пушится:

```bash
python scripts/ota_historical_replay.py run ~/tf-replay           # стенд: ~/tf-replay/stand
git worktree add --detach /tmp/tf-historical-apk origin/main
cd /tmp/tf-historical-apk
#  BundledDatasets.kt:        PRODUCT_BUNDLE.clientBuild = "1.60.1.70374";
#                             убрать "1.60.1.70450" из BUNDLED_CLIENT_BUILDS
#  scripts/mobile_bundles.py: убрать "1.60.1.70450" из BUNDLED_BUILDS
#  удалить mobile/composeApp/src/commonMain/composeResources/files/{dataset,visuals,tooltips,localization}/forever/1.60.1.70450
for k in datasets visuals tooltips localization; do python3 scripts/sync_mobile_$k.py --check; done
cp <checkout>/mobile/local.properties mobile/
python <checkout>/scripts/ota_staging_stand.py activate ~/tf-replay/stand 1-a-staged
python <checkout>/scripts/ota_staging_stand.py serve ~/tf-replay/stand --port 8443   # отдельный терминал
source ~/tf-replay/stand/android-staging.env          # эмулятор: https://10.0.2.2:8443
cd mobile && ./gradlew :composeApp:assembleDebug -Ptalentforge.applicationIdSuffix=.otareplay
unzip -l composeApp/build/outputs/apk/debug/composeApp-debug.apk | grep -c 1.60.1.70450   # 0
adb install -r composeApp/build/outputs/apk/debug/composeApp-debug.apk
```

Физическое устройство: `adb reverse tcp:8443 tcp:8443` и
`TALENTFORGE_OTA_ANDROID_STAGING_BASEURL=https://localhost:8443` перед сборкой
([android-device-smoke.md](android-device-smoke.md) §1.3). Суффикс `.otareplay` ставит отдельное
приложение со своими данными, установленный TalentForge пользователя не затрагивается. Пока
переменные `TALENTFORGE_OTA_*` заданы, любая release-сборка останавливается в
`checkReleaseOtaSettings`.

Шаги и ожидаемый результат — таблица §6, шаги 1–10. Состояние клиента:
`adb shell run-as io.github.alexeykravtsov95.talentforge.otareplay cat no_backup/ota/v1/state.json`.
Для физического устройства дополнительно: фон и foreground во время загрузки, мобильная сеть,
офлайн-старт ([android-device-smoke.md](android-device-smoke.md) §3, шаги 5–7, 11).

Уборка: `adb uninstall io.github.alexeykravtsov95.talentforge.otareplay`,

## 8. Ограничения

1. **main уже содержит 70450.** Подготовка идёт в клоне текущего `main`, где 70450 закоммичен,
   поэтому шаги pipeline воспроизводят его, а не создают впервые. Существующая логика
   (`keep_committed_dataset` и сравнение визуалов по смыслу из PR #72) требует совпадения по
   смыслу и сохраняет байты main. Это доказывает воспроизводимость, но первая нормализация новой
   сборки «с нуля» здесь не моделируется. Реконструкция исторического `main` без 70450 потребовала
   бы откатить бандл приложения, фикстуры и тесты в клоне; это отвергнуто как подмена эталонных
   данных.
2. **G7 и approval-запись.** `docs/ota/releases/1.60.1.70450-r1.md` появилась после патча, а в
   replay она уже есть, поэтому G7 = PASS. В момент реального патча G7 был бы FLAG — обязательным
   шагом человека.
3. **Источник данных — живой wago.tools.** Фазы обнаружения, staging и клиента работают офлайн и
   воспроизводимы. Шаги источника подготовки скачивают DB2 и иконки исторической сборки 70450 с
   wago.tools. Если он недоступен, подготовка получает статус `UNKNOWN`, а replay — `BLOCKED`, но
   не PASS. Данные исторической сборки не меняются, и это проверяют P2–P5.
4. **Production-guard читает реальный production** (два анонимных GET). Опция
   `--no-production-guard` отключает чтение (G2 → NOT RUN). Тайм-аут, сетевая ошибка, ответ не
   200 или любое другое исключение при чтении до начала или после конца replay дают G2 = BLOCKED
   с причиной; `replay-report.json` и `summary.md` пишутся всё равно, тела прочитанных каталогов
   лежат в `guard/`, traceback — в `logs/guard-*-crash.txt`, оба чтения — в
   `facts.productionGuard`. Каталог, изменившийся между чтениями, — тоже BLOCKED, а не FAIL:
   replay не держит production-ключей и публикует только в локальный staging-стенд, поэтому это
   внешнее изменение, и guard не может подтвердить, что production не трогали. PASS только при
   двух прочитанных и равных каталогах.
5. **JVM, не Android.** Автоматическая клиентская часть — реальный код `jvmCommonMain`, тот же,
   что работает на Android, но без Android TLS-стека, `noBackupFilesDir` и жизненного цикла
   Activity. Это частично закрыто ручным прогоном на эмуляторе API 35 (§6). API 26 и физическое
   устройство — NOT RUN.
6. **Время тестов.** Сценарии с обрывом сети идут около 95 с каждый: это настоящие паузы
   повторных попыток клиента (M5.OTA.4c), они не сокращались. Весь клиентский набор — около 7 мин,
   весь replay — около 10 мин.
7. **Workflow на GitHub.** Он стартует на этом PR по `pull_request`; его результат указывается в
   описании PR и не входит в этот отчёт.
