# OTA staging setup (M5.OTA.4a local stand, M5.OTA.4b VK Cloud)

How to run the OTA **staging** channel end to end without any cloud account: the real publisher
(M5.OTA.2) publishes into a local store, a local HTTPS origin serves it, and the real client
(M5.OTA.3) installs from it — on the JVM in tests, and on an Android debug build on an emulator
or a device. Production stays disabled throughout; nothing here can sign or publish for production.

Two staging origins exist. The **local stand** (§2–§5) proves the two implementations against each
other over real TLS without any account. The **remote staging origin** (§6, M5.OTA.4b) is the public
one: VK Cloud Object Storage over its public HTTPS host, written by the same publisher through the S3
adapter. Only the remote one counts as "public HTTPS verified".

## 1. The three kinds of keys

| Kind | Key ids | Where the private key lives | Accepted by |
| --- | --- | --- | --- |
| Fixture | `test-primary`, `test-backup` (`test-*`) | derived from public seeds (`scripts/generate_ota_fixtures.py`); anyone can sign | contract tests only. Every app configuration refuses them (`TEST_KEY_IN_APP_KEYRING`, and the Gradle settings rules) |
| Staging | `tf-staging-*` (the local stand: `tf-staging-local-<hex>`) | the local stand: generated by `scripts/ota_staging_stand.py prepare` as a PEM with mode 0600 in the stand directory, **outside any git checkout** (the script refuses an output inside one). A remote staging key (§6) is a CI or owner secret (OD-2) | staging-channel clients only. Production refuses them (`KEY_NOT_FOR_CHANNEL`, Gradle rules) |
| Production | `tf-prod-<yyyy>a`, `tf-prod-<yyyy>b` | not generated (OD-2): an offline signer; the publisher never loads one (inline signing accepts `test-*`/`tf-staging-*` only) | production clients only, with a backup key |

The stand never generates, reads or needs a production key, and no catalog it writes is a
production catalog (`stage` writes the staging channel only; `promote` is never called).

## 2. Prepare the stand

```bash
pip install -e '.[dev]'                       # in this checkout (or PYTHONPATH=src)
python scripts/ota_staging_stand.py prepare ~/tf-ota-stand
```

`prepare` (≈ 5 s, offline) runs the publisher CLI `talent-data ota …` over the committed data of
`git merge-base HEAD origin/main` (`--commit` overrides it; `--now` fixes the publication instant,
otherwise the wall clock):

| Step | Publisher commands | Result (snapshot of the store) |
| --- | --- | --- |
| A | `build-release` 70374 → `validate` (G1–G8, staging) → `stage` → `verify-live` | `stores/1-a-staged`: sequence 1, A active |
| B | `build-release` 70450 → `validate` → `stage` → `verify-live` | `stores/2-b-staged`: sequence 2, A and B listed, B active |
| rollback | `rollback --channel staging --active A` → `sign` (staging key) → `attach-signature --channel staging` → `verify-live` | `stores/3-rollback-a`: sequence 3, A active, nothing unlisted |
| G6 | a scratch clone commits the wire-valid `release-open-union-node-type` paladin tree on a local `origin/main`; `build-release` 70450-r3 → `validate` → `stage` | both exit 1 with **G6 STOP** (`UNSUPPORTED_NODE_TYPE`) and no other STOP; the store stays byte-identical; the release is listed nowhere |
| level 2 | `build-release` 70450 `--revision 2 --min-data-level 2` → `validate` → `stage` | `stores/4-level-2`: sequence 4, B-r2 active (G6: "data level 2 has no baseline yet: staging may carry this release … but it cannot be promoted") |

The stand directory then holds:

```
keys/staging-keyring.json          public keyring {"keys":[{keyId, algorithm, publicKeySpki}]}
keys/tf-staging-local-<hex>.pem    private staging key (0600)        never commit
tls/ca.pem                         the stand's CA certificate: the only trust anchor of a test client
tls/server.pem, tls/server.key     server certificate (localhost, 127.0.0.1, 10.0.2.2) + key (0600)
stores/<snapshot>/v1/...           the four publications, each a complete static origin
live -> stores/1-a-staged          the snapshot `serve` answers with
work/                              the publisher's live store, built manifests, the G6 clone
report.json                        what was published (sequences, manifests, G6 verdict, key id)
android-staging.env                the Android debug-build settings (§4)
```

The CA's private key is never written: it signs the server certificate in memory and is
discarded, so nothing can issue another certificate under it. The certificates are valid for 30
days from `prepare`, on the wall clock.

## 3. Serve it over HTTPS

The publisher's store **is** the static export: `LocalDirectoryStore` object keys are exactly the
URL paths of contract §1 (`v1/channels/staging/catalog.json`, `v1/blobs/sha256/<hex>`), so the
directory is served as it is — no adapter, no copy.

```bash
python scripts/ota_staging_stand.py activate ~/tf-ota-stand 2-b-staged   # one atomic switch
python scripts/ota_staging_stand.py serve ~/tf-ota-stand --port 8443      # binds 127.0.0.1
curl --cacert ~/tf-ota-stand/tls/ca.pem https://localhost:8443/v1/channels/staging/catalog.json
```

The origin answers `GET` on the two contract paths only, 404 for everything else (including the
production catalog path, `..` and the stand's own files), 405 for other methods, never redirects,
and sets the contract's `Cache-Control` headers. `--blob-delay-ms` slows blob responses so a check
can be interrupted on purpose. `activate` changes which publication is live the way a real
publication changes one catalog object: switch to `3-rollback-a` and the next check rolls back.

TLS is real: TLS 1.2+, a certificate the client verifies against `tls/ca.pem`, the host name
checked. Nothing disables verification; a client that does not pin the stand's CA (any system trust
store) refuses the connection (`tests/unit/ota/test_ota_staging_stand.py`, `OtaStagingE2ETest`).

## 4. Clients

**JVM (automated).** `OtaStagingE2ETest` (composeApp desktopTest, opt-in) runs the real client
against the stand's bytes over HTTPS — its own `HttpsServer` with the stand's certificate, plus
fault injection — with the configuration resolved by `OtaConfig.resolve` exactly as an app build
does, the `HttpURLConnection` fetcher with `pinnedTrustSocketFactory(ca.pem)`, `java.security`
signatures and the `java.nio` store. One command runs everything:

```bash
scripts/ota_integration_check.sh            # --android adds assembleDebug, --keep keeps the stand
```

**Historical replay (M5.OTA.AUTO.2).** `OtaHistoricalReplayTest` runs the same client as the app
*before* 70450 (70374 bundled, the product) against the stand, and
`scripts/ota_historical_replay.py run <out>` chains it with the detection over recorded build
indexes, the real preparation of 70450 and the stand
([M5.OTA.AUTO.2-replay-report.md](M5.OTA.AUTO.2-replay-report.md)).

**Android debug build (manual).** Debug builds read the staging channel
(`GeneratedOtaSettings.androidStaging`). `android-staging.env` sets it for the emulator
(`https://10.0.2.2:8443` reaches the host's `127.0.0.1:8443`), with the stand's keyring and its CA
as the client's only TLS root (`talentforge.ota.android.staging.trustAnchor`):

```bash
source ~/tf-ota-stand/android-staging.env
cd mobile && ./gradlew :composeApp:assembleDebug -Ptalentforge.applicationIdSuffix=.otastaging
```

The suffix installs next to the user's own app, with its own data. Procedure and checks:
[android-device-smoke.md](android-device-smoke.md).

**Release builds never carry it.** Any Android staging setting (`enabled=true`, `baseUrl`,
`keyring`, `trustAnchor`) stops every release variant in `checkReleaseOtaSettings` (wired before
`preReleaseBuild`), because the generated settings are compiled into every variant. A trust anchor
is accepted for the Android staging channel only (never production, never iOS) and must be PEM
certificates without any private key (`verifyOtaSettingsRules` proves each rule). The production
channel stays disabled: no base URL, no keys.

## 5. Plaintext

There is no plaintext path in an app: base URLs must be `https://` (`OtaConfig.resolve` →
`BAD_BASE_URL`, and the Gradle rules), the fetcher refuses any non-HTTPS URL before connecting, and
Android's default network security configuration refuses cleartext. The only plaintext adapter is
`PlatformBlobFetcher(allowLoopbackHttp = true)`, used by tests and the benchmark only, for
`http://127.0.0.1` — not by the staging E2E.

## 6. Remote staging on VK Cloud (M5.OTA.4b)

| | |
| --- | --- |
| Provider (OD-1) | VK Cloud Object Storage, region `ru-msk` |
| Bucket | `talentforge-ota-staging` |
| S3 API (publisher only) | `https://hb.ru-msk.vkcloud-storage.ru`, AWS CLI profile `talentforge-staging` |
| Public origin (clients) | `https://talentforge-ota-staging.hb.ru-msk.vkcloud-storage.ru` — certificate `*.hb.ru-msk.vkcloud-storage.ru` (HARICA DV, chained to HARICA RootCA 2015), trusted by Android 15 and the JVM without a trust anchor |
| Anonymous access | `GET` on `v1/channels/staging/catalog.json` and `v1/blobs/sha256/*` only (bucket policy, set by the owner); the production catalog path, listings and other keys answer 403 |
| S3 key | limited to the `v1/` prefix; lives only in `~/.aws/credentials` |
| Signing key | `tf-staging-2026` (P-256), PEM outside git (`scripts/ota_vkcloud_staging.py keygen`); a separate secret from the S3 key |

No cloud resource, bucket policy, ACL or IAM setting is created or changed by the tooling.

1. **Origin.** As above. There is no CDN and no project-owned hostname: the base URL compiled into a
   staging build is VK's bucket host. The origin compresses `application/json` when asked
   (`Accept-Encoding: gzip`), never redirects, and also answers plain `http://` (the client refuses
   it before connecting).
2. **Store adapter.** `talent-data ota … --backend s3` (`talent_data.ota.s3_store`); procedure and
   guarantees in [publisher-runbook.md](publisher-runbook.md) §6.
3. **Key.** `python scripts/ota_vkcloud_staging.py keygen ~/.talentforge/ota-staging-vkcloud --key-id
   tf-staging-2026 --origin <public origin>` writes the PEM (0600), `staging-keyring.json` and
   `android-staging-vkcloud.env`.
4. **Build.** Internal debug builds only, no trust anchor:

   ```bash
   source ~/.talentforge/ota-staging-vkcloud/android-staging-vkcloud.env
   cd mobile && ./gradlew :composeApp:assembleDebug -Ptalentforge.applicationIdSuffix=.otastaging
   ```

   With these variables set, every release variant still stops in `checkReleaseOtaSettings`.
5. **Proof.** `talent-data ota verify-live --channel staging --backend s3 …`; the JVM client against
   the live origin (`OtaRemoteStagingCheck`, opt-in, one phase per catalog state); the TECNO Spark 40
   ([android-device-smoke.md](android-device-smoke.md) §5). Results:
   [M5.OTA.4b-remote-staging-report.md](M5.OTA.4b-remote-staging-report.md).
